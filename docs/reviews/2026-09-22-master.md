## Summary

This change adds server-side price validation and strict Zod input schema enforcement to the payment creation endpoint. The core security goal is achieved: the server now resolves canonical product prices from lib/datas/productData.ts and completely ignores any client-submitted price. The Zod schema, getProductById helper, and prototype-safety guards are well designed. The test suite is thorough and all 56 tests pass.

However there are two majors that should be fixed before merge. One concerns a real-world IP spoofing risk in rate limiting, and the other is the legacy product schema accepting unexpectedly loose data types (z.any()) that undercuts the strict validation intent.

---

## Major

### 🟠 Rate limit IP is trivially spoofable via x-forwarded-for, pp/api/payment/route.ts:26

**Problem**: The IP address used for rate limiting is taken from the first value of the x-forwarded-for header with no trust configuration. Any client can send x-forwarded-for: 1.2.3.4 in their request and appear to the rate limiter as a different IP on every call. An attacker can trivially bypass the 10 req/min limit by cycling a fake IP in that header.

**Why it matters**: The rate limit is the only authentication-free guard on the Midtrans transaction creation endpoint. A client who bypasses it can fire unlimited payment creation requests, potentially exhausting Midtrans API quota or creating junk invoice records.

**Suggested fix**: Only trust x-forwarded-for when the request comes from a known reverse-proxy tier. Use x-real-ip (set by trusted infrastructure) as the primary source, or use the hosting platform's 
equest.ip equivalent if available (e.g. Vercel). At minimum, document that this endpoint requires a trusted proxy header for safe operation, as the current code gives false assurance.

---

### 🟠 z.any() on product.currency weakens strict validation, lib/validations/payment.ts:45

**Problem**: The backward-compat product field includes currency: z.any().optional(). z.any() bypasses Zod's type checking entirely. While the route ignores product.currency, a client can embed arbitrary payload (a function reference, deeply nested object, Buffer) that passes schema validation. This is inconsistent with the spec goal of strict input sanitation.

**Why it matters**: Even though the server discards the value, Zod still materializes the arbitrary input into the validated data object. A future change that accidentally reads product.currency downstream would inherit untrusted data with no type guard.

**Suggested fix**: Use z.unknown().optional() (signals trusted but unknown structure) or z.record(z.string(), z.unknown()).optional(). Both still block prototype-property injections. If the field is never read, remove it from the schema entirely.

## Minor

### 🟡 Snap client singleton not reset on key change, pp/api/payment/route.ts:10-21

**Problem**: snapClient is module-level and never invalidated. In dev, hot-module replacement can reload the module with a new env var but the old singleton persists. Low risk in production (restart required), but worth noting.

**Suggested fix**: Acceptable tradeoff for now. Optionally store the key used at construction time and recreate if it differs.

---

### 🟡 Duplicate type definitions for PaymentRequest, lib/types.ts:58-62 vs lib/validations/payment.ts:36-47

**Problem**: lib/types.ts defines PaymentRequest.product as ProductDetails (required 
ame, price, currency). The Zod schema defines product.name as optional() and product.currency as z.any(). These diverge. AGENTS.md says "shared types live in lib/types.ts. Never duplicate type definitions."

**Suggested fix**: Derive PaymentRequest from z.infer<typeof paymentRequestSchema> and remove the manual interface, or align the manual interface to the Zod schema precisely.

---

### 🟡 Input handlers silently drop non-numeric input, components/TitleGame/ClientTopUp.tsx:151-164

**Problem**: parseInt(value) >= 0 silently discards alphabetic input (NaN >= 0 is false). A user typing an alphanumeric server ID (e.g. "SG01") finds the field unresponsive with no feedback. Also .replace('-', '') removes only the first hyphen (missing global replace).

**Suggested fix**: Determine if server/user IDs are always numeric for all games. If not, remove the parseInt guard or make it game-specific. Add inline validation feedback instead of silent discard.
