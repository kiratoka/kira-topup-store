## Summary

Pembaruan ini menuntaskan tiga lapis keamanan pada rute notifikasi webhook Midtrans, yaitu pembatasan laju request Redis dengan namespace terpisah, verifikasi signature waktu konstan dengan proteksi panjang buffer, serta penanganan idempotensi berlapis. Seluruh kriteria penerimaan dari AC 1 hingga AC 6 terpenuhi secara memuaskan. Masalah race condition dan potensi kebocoran detail internal yang diidentifikasi sebelumnya telah diperbaiki dengan implementasi atomic conditional update dan sanitasi respon yang tepat.

## Minor

### 🟡 Fallback kunci rahasia kosong pada kalkulasi tanda tangan, `app/api/payment/notification/route.ts:53`
**Problem**: Jika variabel `MIDTRANS_SERVER_KEY` tidak terpasang di lingkungan runtime, variabel `serverKey` berubah menjadi string kosong dan proses SHA 512 tetap berjalan tanpa kunci rahasia.
**Why it matters**: Pihak luar yang menyadari ketiadaan kunci rahasia pada lingkungan server dapat membuat tanda tangan palsu yang lolos verifikasi fase kedua. Meskipun panggilan SDK pada fase keempat akan gagal karena otentikasi tidak sah, rute ini sebaiknya menolak permintaan lebih dini saat variabel lingkungan penting belum terkonfigurasi.
**Suggested fix**: Tambahkan validasi eksplisit di awal fase verifikasi, jika `!process.env.MIDTRANS_SERVER_KEY` segera hentikan eksekusi dengan pencatatan log galat konfigurasi dan kembalikan status 500.
### 🟡 Variabel hasil ekstraksi tidak digunakan, `app/api/payment/notification/route.ts:107`
**Problem**: Properti `order_id: orderId` diekstraksi dari objek `statusResponse` namun tidak pernah dirujuk dalam kode berikutnya, karena blok kode di bawahnya tetap menggunakan `order_id` dari body asli.
**Why it matters**: Memicu peringatan linter TypeScript no unused vars saat proses pemeriksaan kualitas kode dijalankan.
**Suggested fix**: Hapus deklarasi alias `order_id: orderId` dari ekstraksi `statusResponse` atau abaikan jika memang tidak diperlukan.

## Nits

- ⚪ `lib/rate-limit.ts:51`, pemanggilan `incr` dan `expire` dilakukan bertahap tanpa transaksi multi atau script Redis, terdapat kemungkinan kecil key tersimpan tanpa masa kedaluwarsa jika server terputus seketika di antara kedua instruksi tersebut.

## Strengths

- Verifikasi signature waktu konstan dirancang dengan sangat cermat, penambahan guard panjang buffer sebelum pemanggilan `crypto.timingSafeEqual` menghindarkan sistem dari crash runtime akibat perbedaan panjang buffer.
- Penanganan idempotensi berlapis bekerja secara efektif, pemeriksaan awal status final menghemat sumber daya eksternal, sedangkan perintah `updateMany` dengan filter status bukan akhir mencegah kondisi balapan saat webhook paralel tiba bersamaan.
- Pembatasan laju request terisolasi dengan baik melalui awalan `rate-limit:webhook`, memastikan lonjakan webhook tidak mengganggu kuota pengguna pada proses checkout.
- Respon galat internal berstatus 500 telah disanitasi penuh sehingga aman dari kebocoran jejak teknis sistem.
