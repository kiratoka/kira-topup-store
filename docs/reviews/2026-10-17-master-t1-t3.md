## Summary

This change addresses three HIGH severity security findings (T1, T2, T3) from the security audit. T1 adds Redis rate limiting (30 req/min) and PII masking (email obfuscation + token redaction) to both invoice GET endpoints. T2 replaces a race prone INCR/EXPIRE sequence with an atomic Lua script that includes TTL self healing. T3 restricts the CSP `img-src` directive and Next.js `images.remotePatterns` from open wildcards to explicit trusted domains. Overall quality is solid: the changes are minimal, focused, well documented, and backed by comprehensive tests (42 pass, 0 fail). A few minor items worth noting but nothing blocks merge.

## Minor

### 🟡 Shared rate limit bucket across two invoice endpoints, `app/api/invoice/route.ts:11` and `app/api/invoice/[orderId]/route.ts:14`

**Problem**: Both invoice endpoints use the same Redis key prefix `rate-limit:invoice` with the same 30 req/min budget. A client fetching the invoice list and then the detail for a single order consumes from the same bucket. This means 30 combined requests across both endpoints, which could lock a legitimate user out earlier than expected if both endpoints are used in quick succession (e.g. polling the invoice list + detail page).

**Why it matters**: In the current flow this is likely fine because the invoice page typically hits one endpoint at a time. But if a future feature polls both (e.g. real time payment status update), the shared bucket could cause false 429s for normal usage.

**Suggested fix**: Consider using distinct key prefixes (e.g. `rate-limit:invoice-list` and `rate-limit:invoice-detail`) or acknowledge this as an intentional design choice in a comment. Low urgency since the current 30/min budget is generous for a single user.

### 🟡 `getClientIp` returns `'unknown'` when no headers present, shared bucket for headerless requests, `lib/rate-limit.ts:34`

**Problem**: When no IP headers are present (edge case: direct access without a reverse proxy), `getClientIp` returns `'unknown'`. This means all such requests share a single rate limit key `rate-limit:invoice:unknown`, creating a global bucket that could unfairly lock out unrelated users.

**Why it matters**: In production behind Netlify/Vercel, there will always be forwarded headers, so this is likely a non issue. But in local development or unusual deployment scenarios, the `unknown` fallback could cause confusion. The current "fail open" strategy on Redis errors is correctly generous, but the `unknown` IP key works in the opposite direction (accidentally strict).

**Suggested fix**: Document the assumption that the app always runs behind a reverse proxy that sets IP headers. Alternatively, consider failing open (skipping rate limit) when IP is `unknown`.

### 🟡 `maskEmail` does not validate email format beyond checking for `@`, `lib/masking.ts:13`

**Problem**: The function only checks for the presence of `@` and takes the first character of the local part. Malformed inputs like `@domain.com` (empty local part, `atIndex === 0`) are handled (returns as is), but edge cases like `user@@domain.com` or `user@domain@extra.com` would produce odd but harmless results.

**Why it matters**: Since this is a display level masking function and not a validator, the current behavior is acceptable. The function is called only after Prisma returns stored data that was already validated at write time by Zod. This is a defense in depth note, not a bug.

**Suggested fix**: No action needed unless the function is reused in contexts where input is not pre validated. A brief comment noting "expects valid email from database, not a full validator" would clarify intent.

### 🟡 `sanitizeInvoice` uses spread to shallow copy, `lib/masking.ts:45-49`

**Problem**: The function creates a new object via spread (`{ ...invoice, token, customer }`), which correctly avoids mutating the original. However, the `customer` sub object is also shallow copied (`{ ...cust, email }`), so deeply nested properties within `customer` (if any exist) would still share references with the original.

**Why it matters**: Currently the Prisma `customer` field is a JSON column with flat structure (email, userId, gameId), so this is not a problem. But if the schema evolves to include nested objects within `customer`, the shallow copy could lead to unintended mutation.

**Suggested fix**: Acceptable as is. Document the shallow copy assumption if the `customer` schema grows.

## Nits

- ⚪ `app/api/invoice/route.ts:46` and `app/api/invoice/[orderId]/route.ts:48`: `console.error` statements log to stdout in production. Already noted as R1 in the security scope; consistent with the current codebase pattern but worth addressing together with S1 (conditional Prisma logging).

- ⚪ `lib/rate-limit.ts:56-66`: The Lua script is exported as a named constant (`RATE_LIMIT_LUA_SCRIPT`), which is clean for testing. Consider adding `as const` for extra type narrowness, though the tests already assert content directly so this is purely stylistic.

- ⚪ `next.config.ts:37`: The `img-src` directive string is quite long on a single line. Consider breaking it across multiple lines for readability using an array `.join(' ')` pattern. Purely cosmetic.

- ⚪ `lib/rate-limit.ts:90`: `Number(result) || 0` silently coerces unexpected values (strings, null) to 0, which is the safe default (allows the request). This is defensive and correct, but a brief comment on why `|| 0` is chosen over throwing would help future readers.

## Strengths

- **Atomic Lua script** (T2) is textbook Redis rate limiting: INCR + conditional EXPIRE with TTL self healing in a single atomic operation. The self healing for `TTL == -1` is a nice touch that handles edge cases most implementations miss.
- **Fail open design**: Both Redis unavailability (`getRedis() → null`) and Redis errors are handled by allowing the request through. This correctly prioritizes availability over strictness for a payment adjacent flow.
- **Clean separation of concerns**: `lib/masking.ts` is a pure utility with no side effects, easily testable and reusable. The `sanitizeInvoice` generic type constraint (`T extends { status, token?, customer? }`) preserves the full invoice type through the transform.
- **Comprehensive test coverage**: 42 tests across 5 files covering happy paths, edge cases (empty orderId, boundary limit = count), error states (Redis down, DB failure), rate limit enforcement verification, and security assertions (no PII leakage, token redaction). The test for `count === limit` (allowed) vs `count > limit` (blocked) is a good boundary test.
- **CSP hardening** (T3) is minimal and precise: replaced a single `https:` wildcard with an explicit domain list that exactly matches `remotePatterns`. The test asserts both the absence of the wildcard and the presence of each required domain.
- **Spec adherence**: All acceptance criteria from specs 0006 and 0007 are met and verified by tests tagged with AC references.
